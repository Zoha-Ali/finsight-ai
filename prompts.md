The 75 figure is empirically bounded, not a guess: with the new max_tokens, a 100-item statement extracted cleanly (9512-char response, valid JSON, stop_reason=end_turn) while a 130-item one reliably truncated around item 80-84 (stop_reason=max_tokens) - 75 leaves meaningful margin below the confirmed-good 100. Verified all three scenarios live against the real Sonnet API (no mocking): 130 items -> stop_reason=max_tokens detected -> clean rejection with exactly 1 API call (no wasted retry); 100 items -> extracted cleanly then rejected by the explicit cap with the exact count (100) and limit (75) in the message; 45 items (well under the cap) -> succeeded end-to-end exactly as before (45 found, 35 expenses added, 10 deposits skipped), confirming the fix doesn't regress normal uploads.
